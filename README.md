# Fraud Detection with an Investigation Agent

A model that flags likely-fraudulent card transactions, a flagging threshold picked using
real dollar tradeoffs, and an AI "investigation agent" that drafts a case note for a human
fraud analyst for each flagged transaction.

Built entirely with free tools - a hands-on exploration of the kind of SQL + ML + agent work
a bank's Data & AI team does.

## Status

Stages 1-6 complete. See `RESULTS.md` for real numbers from every stage.

## Data

[IEEE-CIS Fraud Detection](https://www.kaggle.com/competitions/ieee-fraud-detection) — about
590,000 real (anonymized) card transactions, about 3.5% fraud, from Vesta Corporation via a
Kaggle competition run with IEEE Computational Intelligence Society.

Two CSV files, joined by `TransactionID`:
- `train_transaction.csv` — one row per transaction (amount, card type, product, etc.)
- `train_identity.csv` — extra device/identity info, only present for ~24% of transactions

Many columns are anonymized (named like `V1`, `V2`, ...) — Vesta does not disclose what they
mean, so this project never guesses at their meaning; see `data_dictionary.md` (coming in
Stage 2).

**Raw data is not in this repo** (too large for GitHub, and re-distribution isn't allowed by
the dataset's terms). To reproduce:

1. Create a free account at [kaggle.com](https://www.kaggle.com).
2. Download the dataset from either:
   - The official competition's Data tab (requires joining the competition), or
   - This plain-dataset mirror with the same 4 files: https://www.kaggle.com/datasets/pranjal101shri/ieee-fraud-detection
3. Unzip the files into `data/raw/` in this repo, so you have:
   - `data/raw/train_transaction.csv`
   - `data/raw/train_identity.csv`
   - `data/raw/test_transaction.csv`
   - `data/raw/test_identity.csv`

## The investigation agent (Stage 6)

For each flagged transaction, the agent calls 4 tools (`scripts/agent_tools.py`) that query
the real data directly — nothing here is guessed or generated by a language model:
1. Recent transactions from the same card
2. Similar past transactions confirmed as fraud
3. How unusual this amount is for that card's history
4. The top SHAP reasons (from Stage 5) for the flag

It then asks a language model to turn that evidence into a short case note
(`scripts/ai_agent.py`), under strict rules: only state facts the tools returned, never
invent cardholder/merchant details, never take an action — only draft a note for a human.
A non-AI template baseline (`scripts/template_baseline.py`) does the same job with fixed
sentence rules, for comparison.

### Limitation: "same card" is approximate, not exact

This dataset has no real card number. "Same card" is approximated by matching 8 columns
together (`card1`-`card6`, `addr1`, `addr2`) — the same approach used by top public
solutions to this competition, since it's the best available with anonymized data. It is
**not exact in either direction**:
- Two different real cards could coincidentally share all 8 values (wrongly merged).
- The same real card could show a different `addr1`/`addr2` if the cardholder's billing
  info changed (wrongly split into two "different" cards).

Every tool result that uses this approximation is labeled `(approximate match)` wherever it
appears, including inside the agent's own notes.

### LLM setup: what we actually used, and why

The original plan was Google AI Studio's free Gemini tier. In practice, its current free
tier allows only **20 requests/day** on the one available model — nowhere near enough for a
25-note evaluation in one sitting (and this number may well be different by the time you
read this — always check https://aistudio.google.com/ for current limits before relying on
it). So this project runs a free model **locally instead**, via
[Ollama](https://ollama.com):

```bash
brew install ollama
brew services start ollama
ollama pull llama3.1:8b
```

No API key, no account, no daily limit, no cost — `scripts/ai_agent.py` just calls
`localhost:11434`. If you'd rather use Gemini (e.g. you only need a handful of notes), the
code structure in `ai_agent.py` would need a small rewrite to call the `google-genai` SDK
instead of Ollama's HTTP API; it isn't included here since it stopped being practical for
this project's evaluation size.

### Evaluation: did the agent actually help?

25 flagged transactions were sampled at random, and both the AI agent's and the template's
notes were checked against the real evidence. **Short answer: the template baseline was
more reliable.** Full honest breakdown, including specific examples of what the AI agent
got wrong, is in `outputs/stage6_evaluation_report.md` and summarized in `RESULTS.md`.
